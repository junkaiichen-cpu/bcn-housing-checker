# BCN Housing frontend integration contract

This contract describes the backend code currently in this repository and its pinned legacy implementation. It is not a promise of production availability or data completeness. Check the deployed `/openapi.json` for the live route list; legacy behavior is loaded at startup from the pinned GitHub commit noted under [Deployment requirements](#deployment-requirements).

## Base URL, JSON, and errors

Set the frontend API base URL to the backend origin, **without** an `/api` suffix. For example:

```env
NEXT_PUBLIC_API_BASE_URL=https://your-backend.example.com
```

```ts
const API_BASE_URL = process.env.NEXT_PUBLIC_API_BASE_URL!;
const response = await fetch(`${API_BASE_URL}/api/properties`);
```

Use JSON request bodies with `Content-Type: application/json`. The public/property workflow uses HTTP status codes and returns endpoint-specific JSON. Validation errors from the new API use this shape:

```json
{
  "detail": [
    {
      "loc": ["body", "transaction_type"],
      "msg": "Input should be 'BUY' or 'RENT'",
      "type": "literal_error"
    }
  ]
}
```

The exact `msg`, `type`, and location are generated by Pydantic and can vary by invalid field. For ordinary API errors, the response is generally `{"detail":"..."}`. Preserved legacy endpoints instead use `{"status":"error","message":"..."}` with HTTP 500 for caught exceptions.

All IDs are strings (UUIDs in the current implementation); timestamps are ISO-8601 strings. Timestamps may contain a UTC offset.

## Authentication and private data

Only `/api/admin/login` is unauthenticated among administrator routes. Every other `/api/admin/...` route requires:

```http
Authorization: Bearer <access_token>
```

Login returns an eight-hour signed bearer token. Store it in the frontend's protected session mechanism, attach it to every admin request, discard it on logout or after a 401, and require login again. There is no refresh or logout API.

Customer requirement contact data is omitted from public submission responses, property responses, matching results, and viewing-submission responses. Admin lead and viewing-list responses include personal contact information and must only be requested in an authenticated admin context.

**Important current limitation:** `GET /api/requirements/{requirement_id}/matches` has no authentication or ownership check; anyone who has a requirement ID can request its matches. It does not return the customer's contact details, but the ID is not treated as an access token. Likewise, `POST /api/viewing-requests` accepts a requirement ID without proving ownership. Do not treat either endpoint as a private customer account API.

## Customer and public-property APIs

### Submit a customer requirement

`POST /api/requirements` — no authentication.

Request JSON (`transaction_type`, `contact_name`, and at least one of `contact_email` or `contact_phone` are required):

```json
{
  "transaction_type": "RENT",
  "budget_min": 900,
  "budget_max": 1600,
  "preferred_locations": ["Barcelona", "Eixample"],
  "property_type": "apartment",
  "bedrooms_min": 1,
  "area_min_sqm": 45,
  "timeline": "Within 2 months",
  "additional_requirements": "Prefer a lift",
  "preferred_language": "zh",
  "contact_name": "Demo Customer",
  "contact_email": "customer@example.test",
  "contact_phone": "+34 600 000 000"
}
```

Request constraints: transaction is `BUY` or `RENT`; budgets are optional, finite, and non-negative, and `budget_min` cannot exceed `budget_max`; locations are up to 20 strings, each at most 160 characters after trimming; property type is up to 80 characters; bedrooms are 0–20; area is greater than 0 and at most 10,000 m²; timeline up to 200 characters; additional text up to 3,000; language defaults to `"zh"` and is 2–20 characters; name is 1–160 characters; email is validated when supplied; phone accepts a restricted set of characters and at least six digits. Do not send an empty string as a contact method.

Success: HTTP `201`.

```json
{
  "id": "requirement-uuid",
  "lead_id": "lead-uuid",
  "transaction_type": "RENT",
  "created_at": "2026-11-09T20:00:00+00:00",
  "message": "Requirement received"
}
```

No contact fields are returned. The backend creates a lead with status `NEW` at the same time.

Possible errors: `422` invalid fields or missing contact method; database/server failures are not normalized by a route-specific handler.

### Get requirement matches

`GET /api/requirements/{requirement_id}/matches` — no authentication; see the access limitation above.

Response: HTTP `200`.

```json
{
  "requirement_id": "requirement-uuid",
  "matches": [
    {
      "property_id": "property-uuid",
      "match_score": 100.0,
      "is_match": true,
      "explanations": [
        "Transaction type matches (RENT)",
        "Price is within the stated budget",
        "Property is in a preferred location",
        "Property type matches",
        "Bedroom count meets the minimum",
        "Property area meets the minimum"
      ],
      "incompatible_requirements": [],
      "missing_or_unverified": [],
      "score_is_not_a_guarantee": true,
      "property": {
        "id": "property-uuid",
        "transaction_type": "RENT",
        "title": "[DEMO] Example two-bedroom apartment",
        "description": "Illustrative demo record only; not a real listing.",
        "location": "Barcelona",
        "neighborhood": "Eixample",
        "price": 1800.0,
        "area_sqm": 75.0,
        "bedrooms": 2,
        "bathrooms": 1,
        "property_type": "apartment",
        "condition": "good",
        "floor": null,
        "has_elevator": true,
        "images": [],
        "source": "DEMO ONLY",
        "data_label": "DEMO",
        "status": "AVAILABLE",
        "created_at": "2026-11-09T20:00:00+00:00",
        "updated_at": "2026-11-09T20:00:00+00:00"
      }
    }
  ],
  "match_count": 1,
  "excluded_properties": [],
  "message": null,
  "method": "deterministic_rules"
}
```

`matches` contains compatible properties, sorted by score descending. `excluded_properties` contains available properties of the same transaction type that failed one or more specified hard criteria, with incompatibilities explaining why. If there are no matches, `matches` is empty, `match_count` is `0`, and `message` says no available properties match; exclusions may still be present. If there are no compatible transaction-type properties, both arrays can be empty. Missing customer criteria and unverified free-text requirements are identified in `missing_or_unverified`. Scores are normalized across criteria the customer supplied; they are not guarantees. Weights are configured at backend process start with `MATCH_WEIGHT_BUDGET` (35), `MATCH_WEIGHT_LOCATION` (25), `MATCH_WEIGHT_PROPERTY_TYPE` (15), `MATCH_WEIGHT_BEDROOMS` (15), and `MATCH_WEIGHT_AREA` (10) by default.

Possible errors: `404 {"detail":"Requirement not found"}`.

### Submit a viewing request

`POST /api/viewing-requests` — no authentication; the supplied requirement ID is not checked for ownership.

Request JSON:

```json
{
  "requirement_id": "requirement-uuid",
  "property_id": "property-uuid",
  "preferred_at": "2026-11-15T10:00:00+01:00",
  "customer_notes": "Weekend preferred"
}
```

`preferred_at` and `customer_notes` are optional; notes are at most 2,000 characters. The property must be available and satisfy the requirement's matching rules.

Success: HTTP `201`.

```json
{
  "id": "viewing-uuid",
  "status": "NEW",
  "created_at": "2026-11-09T20:00:00+00:00",
  "message": "Viewing request received"
}
```

Possible errors: `404` requirement/property not found or property unavailable; `422` malformed fields or property incompatible with the requirement.

## Administrator APIs

All routes in this section except login require a bearer token. The frontend should treat customer contact data, internal notes, and agent contact information returned by these endpoints as private.

### Admin login

`POST /api/admin/login` — no authentication.

Request:

```json
{"username":"admin","password":"<configured password>"}
```

Response: HTTP `200`.

```json
{
  "access_token": "<signed-token>",
  "token_type": "bearer",
  "expires_in": 28800
}
```

Possible errors: `401 {"detail":"Invalid administrator credentials"}`; `429` after ten attempts per client IP in a rolling 60-second window (per application process); `503` if administrator credentials or signing secret are not configured securely.

`POST /api/admin/properties` — bearer token required.

Required: `transaction_type`, `title`, `location`, `price`, `area_sqm`, `property_type`. Optional fields and defaults are:

```json

  "title": "[DEMO] Example apartment",
  "description": "Illustrative demo record only; not a real listing.",
  "location": "Barcelona",
  "neighborhood": "Eixample",
  "price": 1800,
  "area_sqm": 75,
  "bedrooms": 2,
  "bathrooms": 1,
  "property_type": "apartment",
  "condition": "good",
  "floor": "Middle",
  "has_elevator": true,
  "images": [],
  "source": "DEMO ONLY",
  "data_label": "DEMO",
  "status": "AVAILABLE"
}
```

Constraints: positive finite price up to 1,000,000,000; positive finite area up to 10,000; title and location 1–200 / 1–160 characters; description up to 3,000; bedrooms/bathrooms optional 0–50; image references up to 10, each non-empty and at most 2,048 characters. `data_label` is `DEMO|REAL`; status is `AVAILABLE|UNAVAILABLE|CLOSED`.

Response: HTTP `201`, full property object (see [Property data](#property-data)).

Possible errors: `401` missing/invalid/expired bearer token; `422` invalid input.

### List all properties (admin)

## Existing valuation, regional, and legal-risk endpoints

These legacy endpoints are unauthenticated and are backed by the pinned historical backend. The legacy regional data resolver can fall back to another region when supplied location names do not match; the request may succeed without indicating that fallback. Treat the results as prototype estimates, not legal advice or verified listing data.

The shown description, neighborhood list, and metrics are placeholders illustrating the actual response shape, not quoted production data. The live response includes all configured regional data.

Possible errors: no route-specific error schema is defined.

{

  "rental_type":"entire",
  "comarca":"Barcelonès",
  "municipio":"Barcelona",

## CORS and environment variables

The current app replaces the legacy wildcard CORS middleware with an allowlist from `CORS_ALLOW_ORIGINS`, a comma-separated list. Default: `http://localhost:3000,http://127.0.0.1:3000`. Credentials are enabled; methods are `GET,POST,PUT,PATCH,DELETE,OPTIONS`; allowed request headers are `Authorization` and `Content-Type`. Set the exact browser frontend origins, including scheme and port. CORS is not authentication.

Backend environment variables read by the current code:

| Variable | Purpose | Current behavior |
|---|---|---|
| `CORS_ALLOW_ORIGINS` | Browser origin allowlist | Comma-separated; defaults to local Next.js origins. |
| `DATABASE_URL` | SQLAlchemy database connection | Defaults to `sqlite:///./bcn_housing.db`; SQLite is the implemented/simple deployment target. |
| `APP_ENV` | Demo property seeding | Demo records are seeded only when exactly `demo` (case-insensitive); default behaves as production/no seed. |
| `ADMIN_USERNAME` | Admin login name | Must be set for login. |
| `ADMIN_PASSWORD` | Admin login password | Must be set and at least 12 characters. |
| `ADMIN_TOKEN_SECRET` | HMAC signing secret | Must be at least 32 characters. Keep secret; changing it invalidates issued tokens. |
| `MATCH_WEIGHT_BUDGET` | Match weight | Defaults to 35; must be a non-negative integer. |
| `MATCH_WEIGHT_LOCATION` | Match weight | Defaults to 25; must be a non-negative integer. |
| `MATCH_WEIGHT_PROPERTY_TYPE` | Match weight | Defaults to 15; must be a non-negative integer. |
| `MATCH_WEIGHT_BEDROOMS` | Match weight | Defaults to 15; must be a non-negative integer. |
| `MATCH_WEIGHT_AREA` | Match weight | Defaults to 10; must be a non-negative integer. Weights cannot all be zero. |
| `GROQ_API_KEY` | Optional legacy LLM integration | Enables valuation LLM analysis; legacy comparison/risk endpoints require successful Groq calls. |

`DATABASE_URL`, CORS, and matching weights are read at module import; configure them before starting the process. The SQLite database is initialized on startup. The implementation chmods a file-backed SQLite database to `0600`.

## Deployment requirements and integration limitations

- Python dependencies are listed in `requirements.txt`; run the ASGI app as `main:app`, for example `uvicorn main:app --host 0.0.0.0 --port $PORT`.
- **Startup requires outbound network access**: `main.py` fetches and executes the pinned legacy source from GitHub (`d6a31023e6c870280c9d39298143f55435ff3ccf`) during import. A network restriction or GitHub outage can prevent app startup.
- Set administrator credentials, a unique `ADMIN_TOKEN_SECRET` of at least 32 characters, `DATABASE_URL`, and `CORS_ALLOW_ORIGINS` in the hosting environment; never put backend secrets in frontend-exposed `NEXT_PUBLIC_*` variables.
- The default persistence is a local SQLite file. The deployment must use a persistent writable filesystem and a single app instance/process model suitable for SQLite. Ephemeral storage loses data on redeploy; horizontal replicas do not share the database.
- New API schema errors are `422`; malformed/unknown legacy values may instead silently resolve/fallback or return `500`. OpenAPI is available at `/openapi.json`; interactive docs are at `/docs`.
- There is no public single-requirement retrieval, customer account/authentication, or requirement ownership verification. Matching and viewing submission are ID-based only.
- There is no property edit endpoint, no single-agent retrieval endpoint, no viewing-request detail endpoint, and no separate viewing delete endpoint. Property availability and agent active/verified status can be updated via the admin endpoints above.
- Property image and viewing report fields accept references only; no file upload, type/size inspection, or video hosting is implemented.
- Rate limiting applies only to admin login, in process memory; it is not distributed deployment-wide.
- Legacy valuation/risk/comparison endpoints may expose exception text in their 500 responses. Rental-risk contract text can be sent to the third-party Groq integration when configured.
- The legacy API models do not consistently constrain numeric values or enum strings; frontend validation should improve UX, but server behavior is as documented and should not be assumed stricter.

## Quick frontend flow

1. `GET /api/properties?transaction_type=RENT` to display available listings.
2. `POST /api/requirements`; retain response `id` and `lead_id` in the submission flow.
3. `GET /api/requirements/{id}/matches`; show `match_score` with an explicit non-guarantee caveat.
4. `POST /api/viewing-requests` with the requirement ID and selected property ID.
5. Admin signs in at `POST /api/admin/login`; retain the bearer token.
6. Admin fetches `GET /api/admin/leads`, reviews `GET /api/admin/leads/{lead_id}`, then creates/lists agents, assigns one, updates status, and manages viewing requests using the protected APIs above.

The `/api` submission/matching/viewing APIs do not authenticate the customer or prove ownership. Do not present them as a secure customer portal.
